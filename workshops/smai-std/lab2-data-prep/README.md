# Lab 2 – Data Prep

**Persona:** Data Engineer

Prepare data for downstream model building using several approaches so you can pick the right tool for the workload. This lab covers two datasets:

- **Bank Marketing dataset** (UCI) — tabular dataset (~41K records, 20 features), used by Lab 3A (traditional ML with XGBoost)
- **Summarization instruction dataset** — either Databricks Dolly 15K filtered for summarization, or an equivalent corpus generated offline; used by Lab 3B (LLM fine-tuning)

All options produce outputs in **Amazon S3**. For the Bank Marketing dataset, a shared Iceberg registration step persists the data into **S3 Table Buckets** and **Athena Iceberg tables** for downstream analytics, drift monitoring (Lab 5), and QuickSight dashboards.

## Workflow

### Lab 2A — Summarization dataset (LLM fine-tuning prep)

`lab-2a-fine-tuning-data-prep.ipynb` supports **two interchangeable data sources**, chosen with one flag in Section 1. Both produce the same output contract at the same S3 path, so Lab 3B runs unchanged either way.

| `DATA_SOURCE` | Corpus | Needs the internet? | Teaches |
|---|---|---|---|
| `"dolly"` | Databricks Dolly 15K, filtered to the summarization category (~1,190 records) | Yes — Hugging Face Hub | Acquiring, filtering, and validating a third-party corpus |
| `"synthetic"` | Generated by `synthetic_corpus.py` (1,200 records, 6 domains) | No | Designing a corpus when no suitable dataset exists |

Only the acquisition step branches. Everything after it is shared:

1. **Acquire** — load Dolly from the Hub, *or* generate a seeded, reproducible corpus (standard library only; no network, no API key, no model endpoint)
2. **Run quality gates** — schema, minimum length, groundedness, compression ratio, exact and near-duplicate detection
3. **Prove the gates fire** by injecting six deliberately defective records, one per gate
4. **Profile** the dataset, including context length against Lab 3B's 1024-token input budget
5. **Split** 70/30 stratified by domain, then verify there is no train/test leakage
6. **Write and upload** `train.jsonl`, `test.jsonl`, `template.json`

**Enforcement differs by source, deliberately.** Schema, length, and duplicate gates are enforced for both. Groundedness and compression are *enforced* for the synthetic corpus but *advisory* for Dolly — because you own the generator, so a groundedness failure there is a template bug to fix at the source, whereas Dolly's summaries are human-written and abstractive, and people legitimately paraphrase. Enforcing strict groundedness on Dolly would discard a large share of a perfectly good corpus and bias what survived toward extractive summaries.

The numbers make the contrast concrete. Dolly: 1,188 records in, 75 dropped (33 duplicate contexts, 23 contexts under 25 words, 18 responses under 8 words) and 877 advisory flags. Synthetic: 1,200 in, 0 dropped — records are grounded by construction, since a summary can only cite facts the generated context states.

Those 41 Dolly schema failures are the "validate — remove empty or too-short records" step this lab always claimed but never performed.

> **Tradeoff on the synthetic path:** template-generated text has narrower phrasing variety than human writing. The fine-tuned model learns the summarization behavior and shows a clear contrast against the base model in Lab 3B, but not the stylistic range of a real corpus. The notebook's closing section covers when to step up to a teacher-model approach.

### Lab 2F — Iceberg registration (shared step)

Lab 2F (`lab-2f-iceberg-registration.ipynb`) is the **single shared step that every Bank Marketing path (2B–2E) finishes with**. Whichever tool you used to produce `train.csv` / `test.csv`, you then run 2F exactly once to publish that data into the Iceberg layer the rest of the workshop consumes. It does **not** prepare data itself — it reads the CSVs and writes them into pre-provisioned tables.

What it does:

1. **Reads** the processed `train.csv` / `test.csv` from the shared S3 paths produced by 2B–2E
2. **Writes** them into the Iceberg tables (`training_data`, `evaluation_data`) in both the S3 Table Bucket and the default Glue catalog — these tables are pre-provisioned by the `5-data-prep.yaml` CloudFormation stack, so 2F only writes data
3. **Captures snapshot IDs** that Lab 3 and Lab 5 pin as frozen baselines (`FOR VERSION AS OF`)

Run order: **one of 2B–2E → then 2F**. Lab 3 and Lab 5 read the Athena/Iceberg tables that 2F populates, so 2F is required regardless of which prep option you chose.

> **Coming from Lab 2E (Canvas)?** Canvas exports a header-included CSV, so 2F includes an optional, clearly-labeled normalization cell near the top that reshapes the Canvas export into the headerless, target-first layout the rest of the notebook expects. Participants arriving from 2B/2C/2D skip that cell.

## Outputs

### Lab 2A outputs (consumed by Lab 3B — LLM fine-tuning)

Produced by `lab-2a-fine-tuning-data-prep.ipynb`, from whichever `DATA_SOURCE` you selected. The `dolly_dataset` prefix names the lab's slot in S3, not the corpus that filled it — keeping it means Lab 3B needs no edit either way.

- `s3://<DataBucketName>/<ProfileName>/dolly_dataset/train.jsonl` — Training examples
- `s3://<DataBucketName>/<ProfileName>/dolly_dataset/test.jsonl` — Evaluation examples
- `s3://<DataBucketName>/<ProfileName>/dolly_dataset/template.json` — Prompt template for instruction tuning

### Lab 2B–2E outputs (consumed by Lab 3A — traditional ML)

**CSV (regular S3):**
- `s3://<default-bucket>/bank-marketing-lab/data/train/train.csv` — Training data (CSV, no header, target-first)
- `s3://<default-bucket>/bank-marketing-lab/data/test/test.csv` — Test data (CSV, no header, target-first)

**S3 Table Bucket (managed Iceberg):**
- Bucket: `bank-marketing-monitoring-<account-id>`
- Namespace: `bank_marketing`
- Tables: `training_data`, `evaluation_data`

**Default Catalog Iceberg (Athena / QuickSight / Lab 5):**
- Database: `bank_marketing`
- Tables: `training_data`, `evaluation_data`
- Queryable via: `SELECT * FROM bank_marketing.training_data LIMIT 10;`
- Supports time travel: `FOR VERSION AS OF <snapshot_id>`
